<objective>
Fix iOS CI at its root cause: replace the two hardcoded toolchain pins in `.github/workflows/ios.yml`
with run-time resolution, and prove the whole iOS path green on a real `macos-latest` runner.

This is the phase tracer. It is the thinnest slice that touches every layer the phase modifies —
workflow trigger config, runner-local tool resolution, and the `xcodebuild` invocation that consumes
the resolved values — wired end to end and verified by a live CI run, not by static inspection alone.

Purpose: CI-01. The iOS pipeline is red today. Run 34716324916 failed at `Build iOS App for
Simulator` with `xcodebuild: error: Unable to find a device matching the provided destination
specifier`. That same run's simulator listing shows the runner offers `iPhone 16e`, `iPhone 17`,
`iPhone 17 Pro`, `iPhone 17 Pro Max`, `iPhone 17e` and `iPhone Air` under iOS runtimes 26.2 / 26.4 /
26.5 — the pinned plain model is not on the image at all. Re-pinning to a newer name would break on
the next image rotation, so D-01 and D-02 replace both pins with resolution performed on the runner.

Output: `.github/workflows/ios.yml` carrying dynamic Xcode selection (D-02), dynamic simulator
resolution (D-01) and a concurrency group (D-07), plus a green live iOS CI run proving all three.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub-hosted runner image → workflow shell steps | The runner's own tool inventory (`simctl` JSON output, the `/Applications` listing) is parsed into shell variables that are then interpolated into an `xcodebuild` command line. |
| PR contributor → GitHub Actions runner | Branch and fork code executes on the runner; event context (`github.event.*`) is attacker-influenceable if interpolated into a `run:` block. |

### Flagged assumptions carried into execution

1. **RESEARCH A1 — the `xcrun simctl list devices available --json` schema is unverified.** The
   `jq` filter assumes a `.devices` object keyed by `SimRuntime` identifiers, each holding an array
   of objects with `name` and `isAvailable`. This could not be confirmed locally (no accepted Xcode
   licence on the research machine) and no live `simctl` JSON was available. The filter *was*
   validated against a representative fixture and against the real device inventory printed by run
   34716324916, which confirms the device-name set and the multi-runtime duplication. The live
   dispatch in Task 1 is the empirical resolution: if the schema differs, the `Resolved simulator:`
   log assertion fails immediately rather than silently selecting nothing.
2. **RESEARCH A4 — `jq` presence on whatever image currently backs `macos-latest`.** Confirmed only
   via the `actions/runner-images` README, which rotates on GitHub's schedule. The Task 1 live run
   resolves this the same way: a missing `jq` fails the resolution step outright.
3. **Xcode prerelease ambiguity (D-02).** "Latest installed" is implemented as the highest
   version-sorted `/Applications/Xcode_*.app`. If a runner image ever ships a beta bundle under that
   naming, this selects it. RESEARCH A2 notes the `latest` versus `latest-stable` distinction exists
   in the marketplace-action alternative but not in the shell approach the locked decision uses. No
   filtering was added because CONTEXT.md scoped D-02 to selecting the latest, and adding a
   stability filter would be unrequested scope — surfaced here, and as a prohibition, instead.
