<objective>
Replace the four hardcoded Gradle cache-write policies in `.github/workflows/android.yml` with a
single branch-aware expression (D-04), and add a concurrency group so superseded runs are cancelled
(D-07).

Purpose: CICD-01. The Gradle cache is already configured, but its write policy is currently pinned
per job — three jobs are forced read-only and `build-debug` is forced writable, which means a
pull_request run of `build-debug` writes entries that a later `main` build restores. D-04 collapses
all four onto `${{ github.event_name == 'pull_request' }}`, which evaluates to `true` (read-only) on
PRs and `false` (writable) on push, so only trusted pushes populate the shared cache.

This plan runs in parallel with Plan 01: it touches a different file, and the Android pipeline is
currently green, which makes it the low-risk place to land the two patterns Plan 03 will later apply
to the iOS workflow.

Output: `.github/workflows/android.yml` with one uniform cache-policy expression across all four
jobs and a top-level concurrency block.
</objective>

byte-identical: the previous per-job split disappears, because a `push` event — including a push to
`main` and a merged PR — evaluates the expression to `false` and therefore stays cache-writable,

policy, and it is a security fix as well as a consistency one: `build-debug` currently writes the
shared cache on every PR run.

default. Composite-action metadata is parsed statically and an input default is a literal string, so

Actions coerces to a non-empty, truthy string, silently forcing the cache read-only everywhere. This
is a platform constraint, not a style preference, which is why the value has to live at each call
site.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| PR contributor → GitHub Actions cache service | A job running on a pull_request branch can write cache entries that a later run on `main` restores and builds from. |
| Workflow → `android-setup` composite action | The cache-write policy crosses from the calling workflow into the shared composite action as an input value. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-04 | Tampering | Gradle cache writes from `pull_request` runs, via `build-debug` in `android.yml` | high | mitigate | All four `android-setup` call sites set `cache-read-only` to `${{ github.event_name == 'pull_request' }}`, so no pull_request run can write an entry a later `main` build restores. This directly closes the current exposure: `build-debug` is pinned cache-writable today and therefore populates the shared cache from every PR branch. Enforced by Task 1's gate, which counts four occurrences of the expression and rejects any surviving hardcoded boolean. |
| T-01-05 | Denial of Service | `concurrency` group in `android.yml` | low | accept | `cancel-in-progress: true` lets a rapid push sequence cancel earlier runs. This is the intended cost-saving behaviour D-07 asks for, it is self-healing on the next push, and it affects CI throughput only — no production system depends on a given run completing. The one non-obvious consequence, a cancelled cache-populating run on `main`, is recorded as a prohibition rather than accepted silently. |
| T-01-09 | Tampering | `.github/actions/android-setup/action.yml` | medium | mitigate | The composite action is shared by every Android job and, after Plan 03, by the iOS job as well, so an unintended edit to it changes cache policy repository-wide at once. Task 1's second gate reads the action's own content and fails if it references `github.event_name` or stops forwarding `inputs.cache-read-only`, so the branch-aware expression cannot be silently relocated into the input default where Actions would forward it uninterpolated and coerce it to a truthy string. The check is content-based rather than diff-based so it stays meaningful after the task is committed. |

All `high`-severity threats in this register carry disposition `mitigate`, satisfying the
configured `security_block_on: high` threshold.
</threat_model>
