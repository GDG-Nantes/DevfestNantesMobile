<objective>
Collapse the iOS workflow's duplicated Java and Gradle provisioning onto the shared
`android-setup` composite action (D-05), give that call site the same branch-aware cache policy the
Android jobs now use (D-04), and prove that the reshuffle did not break the invariants this phase
promised not to touch — the Konan cache (D-06, CICD-02) and the two-file, two-runner job separation
(D-03, CICD-03).

Purpose: CICD-01, CICD-02, CICD-03. `ios.yml` currently carries its own `setup-java`, `setup-gradle`
and `local.properties` steps that duplicate what `android.yml` already gets from the composite
action, and its inline Gradle setup is pinned permanently read-only. Routing it through the shared
action removes roughly fifteen lines of duplicated YAML and leaves one place where Java and Gradle
setup is defined for both platforms.

This plan runs in wave 2 because it modifies the same file Plan 01 modifies. It is also the riskiest
remaining edit: the composite action marks its `setup-gradle` step `continue-on-error`, so a
Gradle-setup failure no longer fails that step, and the iOS job's downstream
`./gradlew :shared:embedAndSignAppleFrameworkForXcode` and `xcodebuild` steps are what must be
observed green instead.

Output: `.github/workflows/ios.yml` provisioned through the shared composite action, with the Konan
cache and runner separation asserted intact and a live green run confirming it.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| PR contributor → GitHub Actions cache service | The iOS job can write cache entries that a later run on `main` restores and builds from. |

### Flagged assumptions carried into execution

1. **The `workflow_dispatch` cache-write policy is inferred, not decided.** D-04's wording covers
   only push-to-`main` and `pull_request`. The expression it names evaluates `workflow_dispatch` to
   `false`, i.e. cache-writable. This plan is where that actually takes effect, because `ios.yml` is
   the only workflow in the repository with a `workflow_dispatch` trigger — and this plan's own
   verification dispatches one. A manual dispatch is trust-gated by repository permissions, so
   writable is defensible and is RESEARCH's recommendation, but it is a case CONTEXT.md did not
   decide. Worth one line of user confirmation at phase verification.

   inline Gradle step set it while also pinning the cache read-only, and cleanup only acts on a
   writable cache, so it had no effect to lose. After this change the iOS call site can be
   cache-writable on push and dispatch runs, and the composite action does not set `cache-cleanup`
   at all — matching the four Android jobs. No decision asks to reconcile this, so it is left as-is
   and recorded here rather than changed silently.
